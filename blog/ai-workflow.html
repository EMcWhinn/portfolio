Building documentation automation with AI: a technical writer's toolkit

Edward Mc Whinney Senior Technical Writer 2025

I've been integrating AI tools into my technical writing workflow for about a year now, and it has changed how I work. Not in some revolutionary way where AI is writing our docs, but in a quieter, incremental way where I'm no longer spending half my day on tasks that don't improve documentation quality. Bash scripts. Regex debugging. Tracking which PR got backported to which version. Running the same linter command dozens of times because our docs are modular and nothing checks them all at once.

I kept thinking: there has to be a better way to do this.

I'm a senior technical writer documenting the Ansible Automation Platform, a distributed automation system with multiple components, versioned releases, and modular AsciiDoc documentation. The work involves a lot of actual writing, but also a significant amount of repetitive operational tasks that eat into the time I could spend making docs better.

I started experimenting with Gemini, then discovered NotebookLM for research, and now use Claude Code for building tooling. Using all three together covers most of what I need, though sometimes one tool is enough depending on the task. I'll walk you through how this works in practice.

The tools

Gemini

This was my starting point. I'd paste in code snippets I didn't understand, brainstorm approaches to problems, and generate quick scripts. It got me thinking differently about what I could automate rather than doing manually.

NotebookLM

You upload your own sources — docs, PDFs, meeting notes, design documents — and it creates a knowledge base you can query. This was a game-changer during the documentation cycle leading up to our 2.6 platform launch. I'd upload engineering design docs and existing published documentation, then ask it to synthesize information across those sources. It generates answers grounded in your actual materials, not generic internet knowledge. I use it almost daily now for research, content planning, and learning new features.

Claude Code

This is what I turn to when I need to build something. It runs in the terminal, maintains context across a session, adapts to exactly what you're trying to do, and can reference anything saved locally. It's become my first choice for any implementation work.

Day-to-day workflow

A typical workflow looks something like:

  1. Research (NotebookLM) — Upload relevant engineering docs and existing content, map the problem space
  2. Brainstorming (Gemini) — Talk through approaches, weigh trade-offs
  3. Implementation (Claude Code) — Build the script, tool, or automation
  4. Refinement (all three) — Verify, check, debug when things inevitably break

In practice I skip steps, go back and forth, or sometimes use Claude Code for everything. But having options means I can match the tool to the problem.

A force multiplier, not magic

AI doesn't write our documentation. That still requires understanding our users, clarifying complex concepts, and creating accurate technical content — all the things that actually matter.

But if I'm spending 30 minutes writing a bash script, that's 30 minutes I'm not improving our docs. AI has become my programming partner, editorial assistant, and brainstorming tool. You still have to think. But once you've figured out the right approach, AI helps you build it faster.

Example: recursive Vale linting

Our documentation uses a modular AsciiDoc structure. There's a master.adoc file that includes dozens of assemblies, which include modules and snippets, sometimes three or four levels deep.

When I run Vale (our style guide linter), it only checks the master file. To verify style compliance across all included files, I'd have to manually lint every single one. With hundreds of files across multiple doc sets, this wasn't sustainable.

I started by asking Gemini to sketch out a bash script that recursively parses AsciiDoc include directives and runs Vale on each file. I got a decent starting point — basic logic for parsing includes, rough structure. But when I tested it against a real doc set, it broke on attribute-based includes, missing files, and nested paths.

I took that rough draft to Claude Code and iterated. A few prompts later, it refined the script with better pattern matching, proper recursive function handling, error handling for missing files, and filtering to exclude attribute-based includes. Claude Code accelerated what would have been hours of iteration into a focused working session.

I tested it on a real documentation set and it surfaced hundreds of previously undetected Vale violations. When the initial output was overwhelming, I added the --minAlertLevel=warning flag to filter out suggestions and focus on warnings and errors.

Instead of documenting this in a document that would immediately get lost, I created a GitHub repository with a proper README. Version control for the script itself, clear documentation that lives with the code, and easy sharing through a repo link that other writers can fork and adapt.

The whole process — brainstorming, refining, setting up the repo — took about an hour. Now I run one command and Vale checks every file in the documentation tree. The script runs in our pre-commit workflow, catching style issues before they reach review.

Example: backport verification

We support multiple documentation versions simultaneously — 2.6, 2.5, 2.4. When we merge a fix to main, we backport it to older branches. The manual process was: tag PRs with version labels, create backport PRs, add completion labels, check a weekly build checklist. With dozens of PRs weekly, there was no automated verification that backports were actually completed.

I started by identifying the failure points: too much reliance on human memory, no systematic verification. I brainstormed the approach with Gemini — GitHub Actions vs. standalone script, Slack vs. Jira notifications, weighing the tradeoffs. Then I built it with Claude Code: a Python script that queries the GitHub API, checks version labels against actual backport PRs, and detects mismatches.

In the first month, it caught several PRs with version labels but no corresponding backports — fixes and improvements that customers on older versions would have missed. Every time it catches one, it validates the investment. It's one less manual process the team has to worry about.

What I've learned about making this work

  • Be specific or get poor results. Early on I'd ask vague questions like "write me a script to check files." Now I explain the problem, show input data examples, specify output format, and mention edge cases. The difference in output quality is significant.
  • Always review. AI-generated code works most of the time, but not always. I test with real data and read the code to understand what it's doing. Trust, but verify.
  • Iterate, don't expect perfection. The best results come from conversation — start basic, test with real data, refine based on what breaks.
  • We're still the experts. AI handles implementation details. We handle understanding user needs, defining the right problem, designing the solution, and testing against real scenarios.
  • Document your automations. What problem it solves, how to run it, what to do when it breaks, how to update it later. If it's not documented, it's not maintainable.

The result

I spend less time on

  • Writing boilerplate scripts from scratch
  • Debugging syntax errors
  • Manually tracking backports across versions
  • Running repetitive checks across hundreds of files

I spend more time on

  • Improving documentation structure and information architecture
  • Making complex technical concepts understandable
  • Collaborating with engineering on new releases
  • Writing content that helps users solve real problems

It's been a significant learning curve, and there's plenty more to come. The tools keep evolving, and so does how I use them. The fundamental shift is that I now approach repetitive operational work as an automation problem first, and that mindset — independent of any specific AI tool — has made the biggest difference.
